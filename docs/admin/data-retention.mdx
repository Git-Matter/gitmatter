---
title: Data retention
description: Retention settings, startup cleanup, and the limits of exports and deletion.
---

gitmatter runs best-effort cleanup when the server starts. It has no recurring retention scheduler in the application. Document deletion requests also trigger an opportunistic sweep of eligible documents. A server that stays up does not continuously sweep audit logs, chats, or revoked tokens.

The windows below determine when records become eligible for cleanup, not a guaranteed deletion deadline. Configurable windows use days; setting one to `0` disables that cleanup. Some records have no automatic expiry.

## Retention windows

| Data                     | Variable               | Default               | Measured from                      | Notes                                                                                                                                                                                                                             |
| ------------------------ | ---------------------- | --------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Documents (soft-deleted) | —                      | 30 days               | `deleted_at`                       | Hidden records become eligible for cleanup after 30 days. The sweep attempts to delete version file bytes before removing the database row. This window is not configurable by env; failed file deletion is not proof of erasure. |
| Chat history             | `CHAT_RETENTION_DAYS`  | `0` (keep forever)    | Last activity (`chats.updated_at`) | Pinned chats are never purged. Messages are removed with their chat.                                                                                                                                                              |
| Audit events             | `AUDIT_RETENTION_DAYS` | `365`                 | `audit_events.created_at`          | The security and operations log: logins, token and key lifecycle, OAuth, uploads.                                                                                                                                                 |
| OAuth auth codes         | —                      | Eligible once expired | `expires_at`                       | Startup cleanup removes expired codes; expiry does not trigger an immediate purge.                                                                                                                                                |
| OAuth access tokens      | `TOKEN_RETENTION_DAYS` | `30`                  | `revoked_at`                       | Only **revoked** tokens are purged. A token whose access has merely expired is kept while its refresh token is still valid.                                                                                                       |
| Static MCP tokens        | `TOKEN_RETENTION_DAYS` | `30`                  | `revoked_at`                       | Only **revoked** tokens are purged after the window.                                                                                                                                                                              |

## What is never purged automatically

- **Live tokens** (access tokens that have not been revoked, so they have no `revoked_at` date) are never purged on a timer. Revoke a token to start its retention clock.
- **Bring-your-own-key provider keys** (the AI provider keys a firm supplies itself) have no expiry. They are removed only when the user deletes them.
- **Artifacts** (matters, clients, tabular reviews, workflows) and the **git commit history** (the record of every change) stay until the artifact itself is deleted. They are not on a retention timer.

## Operational notes

- Startup cleanup errors do not block the app from starting. A later startup can retry records that remain eligible.
- A failed object-storage deletion records `storage.delete_failed`, but the document row can still be removed. This path does not establish a durable retry or guarantee that every stored file was erased.
- Lowering a `*_RETENTION_DAYS` value changes eligibility at the next sweep. It does not add a scheduler or establish a deletion deadline.

## Exports and account deletion

Organization admins can download selected client and matter fields, review grids, and a document metadata manifest as CSVs from Settings &rarr; Data &amp; Privacy. The export excludes document files and versions, chats, workflows, commit history, and security audit logs. It is not a complete backup; see [backup and restore](/admin/backup-restore).

Deleting an account is separate from deleting an organization's shared records. Some shared records retain their content with the former author's reference removed. Account removal does not establish erasure of object-storage files, backups, or copies held by external services. The application cleanup windows do not define backup retention.
